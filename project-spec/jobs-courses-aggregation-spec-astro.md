# Jobs & Courses Aggregation Platform

## Astro + GitHub Actions + Cloudflare D1 + Cloudflare Pages

**Implementation specification --- Astro edition**\
**Version:** 1.1 \| **Date:** 15 November 2026

## 1. Purpose and fixed decisions

Build a search-friendly employment and learning-opportunities website
that imports job and course metadata from approved sources, refreshes it
on a controlled schedule, and publishes useful individual pages.

**Architecture decisions** - Keep the existing **Astro** project. Do not
migrate to Next.js. - Use Astro's **static output** for the public
site. - Use Cloudflare D1 as the canonical structured database. - Use
GitHub Actions for scheduled ingestion, export and deployment. - Use
Cloudflare Pages to serve the generated static site. - Articles are
human-written and editorially reviewed; they are not generated by the
ingestion pipeline. - Use free tiers only. Do not enable paid services
or usage-based features without explicit approval. - Respect source
terms, licences, attribution requirements and rate limits.

The site is an aggregator. Visitors should apply or enrol through the
original employer/provider wherever possible.

## 2. Architecture

``` text
Approved RSS / APIs
       |
       v
GitHub Actions (scheduled)
       |
       v
Fetch -> validate -> normalise -> deduplicate
       |
       v
Cloudflare D1
       |
       v
Build-time export of publishable records
       |
       v
Astro static build
       |
       v
Cloudflare Pages -> visitors/search engines
```

Ordinary page views must not query D1 or invoke a Worker. A Worker is
optional later for a search API or protected ingestion endpoint; it is
not required for the first release.

### Astro is the frontend

Astro routes such as `src/pages/jobs/[slug].astro` can generate static
HTML at build time. A dynamic route filename does **not** imply
server-side rendering. In static mode, Astro's `getStaticPaths()`
determines which pages are generated.

Keep Astro configured for static output:

``` js
// astro.config.mjs
import { defineConfig } from 'astro/config';

export default defineConfig({
  output: 'static',
});
```

Do not add the Cloudflare adapter merely to query D1 on each visitor
request. D1 is accessed by the ingestion/build pipeline.

Human-written articles may use Astro Content Collections or the existing

Generated JSON is reproducible build input, not hand-edited content;
preferably create it inside the GitHub Actions workspace rather than
committing it.

### Build-time data flow

Before `astro build`:

1.  Authenticate to Cloudflare using a narrowly scoped API token stored
    in GitHub Actions secrets.
2.  Export approved, publishable records from D1.
3.  Validate the export and write deterministic JSON into the build
    workspace.
4.  Run `astro build`.
5.  Deploy Astro's `dist/` directory to Cloudflare Pages.

Use a supported Wrangler/D1 export or query mechanism for the Wrangler
version in use. Verify the exact command against current Cloudflare
documentation during implementation. Never expose credentials in
generated JSON, browser code or logs.

Illustrative static route:

``` astro
---
import jobs from '../../data/generated/jobs.json';

export function getStaticPaths() {
  return jobs.map((job) => ({
    params: { slug: job.slug },
    props: { job },
  }));
}

const { job } = Astro.props;
---

<h1>{job.title}</h1>
```

The production implementation must also handle missing fields, status,
canonical URLs, structured data and safe rendering. Measure build time
and output size as the dataset grows. Only generate pages for valid,
approved and publishable records.

## 4. Refresh schedule

Maximum frequencies are explicit:

  Content                  Maximum scheduled refresh
  ------------------------ -----------------------------
  Jobs                     Twice per day
  Courses                  Twice per week
  Human-written articles   Manual editorial publishing

Suggested East Africa Time schedule (UTC+3):

  Workflow                            EAT UTC cron
  ------------ -------------------------- ---------------
  Jobs run 1                  Daily 06:15 `15 3 * * *`
  Jobs run 2                  Daily 18:15 `15 15 * * *`
  Courses        Tuesday and Friday 07:00 `0 4 * * 2,5`

GitHub Actions cron is UTC and scheduled jobs may be delayed; these are
target start times, not exact guarantees.

Rules: - Never fetch jobs more than twice in a calendar day. - Never
fetch courses more than twice in a calendar week. - No continuous
polling. - Check expiry from stored data during an existing run/build;
do not add a separate external crawl. - Manual runs are exceptional,
authorised and logged, not routine extra fetches. - Prevent overlapping
workflows with concurrency controls. - Use bounded retries and backoff
for transient failures. - A failed source must not delete existing
records or expire all of its listings. - Log source outcomes, record
counts and deployment decisions.

### Change-aware deployment

A fetch does not automatically justify a rebuild: 1. Compare the
resulting public dataset with the previous state. 2. If no public
data/status changed, do not deploy. 3. If public content changed, export
data, build Astro and deploy once. 4. Do not deploy once per source or
record.

Choose one deployment owner. If GitHub Actions deploys, disable or
coordinate Pages Git-triggered builds to avoid duplicate deployments.

### Indexes and uniqueness

Index jobs by slug, status, closing/publication date, country, category
and work mode. Index courses by slug, availability, subject and
provider. Index ingestion runs by source and start time.

Use a unique constraint on `(source_id, source_record_id)` when the
source ID is stable. Otherwise use a source-specific canonical URL or
deduplication key. Do not merge records merely because titles are
similar.

## 6. Ingestion and data-quality rules

Each source should have an isolated adapter that converts its format
into a common internal record shape.

### Processing sequence

1.  Load enabled sources for the scheduled content type.
2.  Enforce the refresh-frequency policy.
3.  Fetch with timeouts and a descriptive user-agent where required.
4.  Validate response format and source identity.
5.  Parse records.
6.  Normalise fields and dates.
7.  Validate required fields.
8.  Apply source permission rules.
9.  Deduplicate against existing records.
10. Insert new records or update changed records.
11. Reconcile status only when evidence is reliable.
12. Write ingestion and status-history records.
13. Export publishable records if public output changed.
14. Build and deploy only when needed.

### Validation

A job normally needs a recognisable title, source URL, employer/hiring
organisation where available, and a usable application destination or
clear application instructions on the source page.

A course normally needs a title, provider, source URL, and a reliable
indication of what the visitor can study. Price/certificate fields may
be explicitly unknown.

Reject or quarantine malformed records. Do not publish placeholder text
as a genuine vacancy/course.

### Deduplication and updates

Use, in order: 1. Stable source ID within that source. 2. Canonical
source URL. 3. A normalised fingerprint using title, employer/provider
and location/subject.

Update changed fields without needlessly changing stable slugs. Preserve
source identity and URL. Use a content hash to avoid unnecessary writes
and builds. Do not overwrite known values with null merely because a
source temporarily omitted a field.

### Failure and disappearance handling

Absence from one feed response is not proof of expiry; feeds may be
incomplete, paginated or temporarily broken.

Reliable expiry/withdrawal evidence includes: - A stated deadline has
passed, with a defined date/timezone interpretation. - The employer's
original page confirms closure. - The source explicitly marks the
listing closed/withdrawn. - A tested, documented source-specific rule is
known to be reliable.

If a fetch fails, retain existing records and statuses. Never infer that
all records disappeared because one request failed.

## 7. Expired vacancy behaviour

An expired vacancy should remain useful rather than becoming a dead-end.

For a known job whose application period has ended: - Keep its URL
accessible if it retains reference value. - Return a normal page
response (HTTP 200 for the generated static page). - Show a prominent
**"This vacancy has expired"** notice. - Show the deadline if known. -
Keep employer, title and source attribution visible. - Disable/remove
the active application call-to-action. - Do not imply applications are
still open. - Link to relevant current vacancies.

Suggested notice:

> **This vacancy has expired.** The application deadline has passed, so
> this listing is retained for reference only. Check the employer's
> website for other opportunities.

Distinguish confirmed expiry from an unverified status.

SEO rules: - Remove active `JobPosting` structured data from expired,
withdrawn or unverified jobs. - Remove them from active job listings and
active-job sitemaps. - Keep an expired page indexable only if it has
meaningful reference value and is not misleading/thin. - A genuinely
deleted record with no useful content may return 404 or 410. - Do not
redirect every expired vacancy to the jobs homepage. - Do not infer a
deadline where none is supplied.

## 8. URLs and page content

Suggested stable URL patterns:

``` text
/jobs/
/jobs/{job-slug}/
/courses/
/courses/{course-slug}/
/categories/jobs/{category}/
/categories/courses/{subject}/
/locations/{country-or-city}/
/articles/{article-slug}/
```

Avoid volatile dates/source IDs in public slugs unless necessary.
Preserve existing URLs when titles change; if a slug must change, add a
permanent redirect.

### Job detail page

Display, when known: - Title and employer. - Location, work mode and
employment type. - Publication date and application deadline. - Salary
only if disclosed. - Accurate permitted description/summary. - Original
source attribution. - Application link only while valid and active. -
Clear expired/withdrawn/unverified state.

### Course detail page

Display, when known: - Title and provider. - Subject and level. -
Delivery mode and language. - Duration. - Course price status and
certificate price/status separately. - Original provider link. -
Last-checked date where useful.

Never invent salary, dates, duration, accreditation, certificate details
or employer/provider information.

### Listing filters

Jobs: location, category, work mode, employment type, employer and
publication/deadline date.

Courses: subject, provider, level, delivery mode, price and certificate
type.

Do not create indexable pages for every arbitrary filter combination.
Keep filter state client-side or apply canonical/noindex rules to
parameterised results.

## 9. SEO and structured data

The objective is useful pages, not mass-produced copies of third-party
sites.

Implement: - Unique page titles and meta descriptions. - One clear
primary heading per page. - Canonical URLs. - XML sitemap index and
appropriate child sitemaps. - robots.txt. - Breadcrumb navigation and
accurate breadcrumb structured data. - Internal links between related
jobs, courses, categories and articles. - Mobile-friendly, fast static
HTML. - Correct missing-page status handling.

Only include canonical, publishable pages in sitemaps.

### JobPosting

Use Google's `JobPosting` structured data only on individual pages for
genuine, current vacancies. Structured data must match visible page
content. Do not invent salary/dates or use the markup on category pages.
Remove it promptly when a job closes.

Official guidance:\
https://developers.google.com/search/docs/appearance/structured-data/job-posting

Google's Indexing API is limited to supported content types such as job
postings and livestream pages; it is not a general indexing API for
courses or articles:\
https://developers.google.com/search/apis/indexing-api/v3/using-api

### Courses

Use course-related Schema.org markup only when the page genuinely
represents a course and all fields are accurate. Structured data does
not guarantee a rich result. Check current Google documentation before
implementation:

https://developers.google.com/search/docs/appearance/structured-data/course-info

### Indexing strategy

Prioritise useful active job pages, useful course pages, curated
category/location pages with enough unique value, and original
human-written articles.

Avoid indexing empty categories, duplicate/thin copies, arbitrary filter
permutations, internal search pages and suppressed/malformed records.
Indexing does not guarantee ranking or traffic.

Human-written editorial articles can cover practical topics such as CV
preparation, legitimate remote-work searches, applying for jobs in
Uganda, and comparing free courses with paid certificates. Articles must
be original and fact-checked, not filler.

## 10. Search implementation

First release: - Generate static listing and category pages at build
time. - For modest datasets, use client-side filtering with a compact
JSON dataset. - Do not send every field for every record to every
visitor. - Split or paginate datasets when payload size becomes
excessive.

Later, if needed, add a Cloudflare Worker search endpoint backed by
indexed D1 queries. Only add it when actual dataset size or usage
justifies it. Validate query parameters, bound result sizes, cache where
sensible and monitor quotas. Static detail-page views must not invoke
it.

## 11. Free-tier and cost safeguards

Free-tier limits and terms change. Verify current official
pricing/limits before launch and periodically afterwards.

Principles: - Static page delivery by default. - No D1 query on ordinary
visitor page views. - No paid scraping services or paid data APIs. - No
always-on server. - No unnecessary Worker invocation. - No rebuild when
public data is unchanged. - Bounded requests, timeouts and retries. -
Store only the data needed and permitted. - Monitor build minutes,
database storage, read/write usage and API requests.

Use free plans only. Do not enable paid add-ons or usage-based services
without explicit approval. Set usage alerts where available and review
usage after the first week and month. If a quota is approached, reduce
scope/frequency before considering a paid tier.

Official references: - Workers limits:
https://developers.cloudflare.com/workers/platform/limits/ - D1 pricing:
https://developers.cloudflare.com/d1/platform/pricing/ - D1 limits:
https://developers.cloudflare.com/d1/platform/limits/ - Pages limits:
https://developers.cloudflare.com/pages/platform/limits/ - GitHub
Actions: https://docs.github.com/en/actions

Do not hard-code quota assumptions into the product. GitHub scheduled
workflows can be delayed; runner allowances depend on repository/runner
configuration.

## 12. Security and reliability

-   Store Cloudflare credentials in GitHub Actions secrets, never source
    files.
-   Use a scoped API token with only required D1/deployment permissions.
-   Never expose secrets in logs or generated assets.
-   Validate and sanitise all external text.
-   Do not trust or render remote HTML as-is.
-   Allowlist URL schemes (`https` preferred) for source/application
    links.
-   Set fetch timeouts and response-size limits.
-   Handle malformed XML/JSON safely.
-   Preserve last known good records when a source fails.
-   Version database migrations.
-   Document and periodically test backup/export recovery.

## 13. Deployment workflow

``` text
Scheduled trigger
    |
    v
Determine content type (jobs or courses)
    |
    v
Fetch approved sources within frequency limits
    |
    v
Validate, normalise and deduplicate
    |
    v
Update D1 and log ingestion
    |
    v
Did public content change?
    |                 |
   No                Yes
    |                 |
 Finish          Export build data
                      |
                      v
                 Validate export
                      |
                      v
                   astro build
                      |
                      v
             Deploy dist/ to Pages
                      |
                      v
              Record deployment result
```

A source-specific failure should be visible in the run report but must
not wipe data from other successful sources.

Choose one deployment owner:

**Option A --- GitHub Actions owns deployment:** workflow exports data,
builds Astro and deploys `dist/` to Pages. Coordinate/disable duplicate
Git-triggered Pages builds.

**Option B --- Pages Git integration owns deployment:** ingestion
updates build input in the repository and Pages builds. Ensure one
controlled commit/deployment per changed batch; never commit secrets.

Option A provides explicit control over ingestion, build and deployment.
Select based on the existing repository.

## 15. Acceptance criteria

The first production release is acceptable when:

1.  The existing Astro frontend is retained; no Next.js migration
    occurs.
2.  The public site is statically generated and served by Cloudflare
    Pages.
3.  At least one approved job source is imported.
4.  Course ingestion is implemented when a suitable permitted source is
    available.
5.  Jobs refresh no more than twice daily.
6.  Courses refresh no more than twice weekly.
7.  Runs are logged and source failures are isolated.
8.  Duplicate records are not repeatedly published.
9.  Existing records survive temporary source outages.
10. Expired jobs show a clear notice rather than a dead-end error.
11. Expired jobs are not shown as open and have no active `JobPosting`
    markup.
12. Individual job/course pages have stable URLs.
13. Sitemaps contain only eligible canonical pages.
14. Source permissions and attribution are respected.
15. Ordinary page views do not invoke Workers or query D1.
16. No deployment occurs when public data is unchanged.
17. Credentials never appear in client assets or logs.
18. Only free tiers are used unless the owner explicitly approves
    otherwise.

## 16. Decisions to settle during implementation

Do not guess these; resolve them from the existing repository and source
terms:

-   Which sources offer the best Uganda/East Africa coverage with
    acceptable reuse terms?
-   Which course sources expose reliable metadata and clear terms?
-   Should the first release include remote/international jobs alongside
    Uganda-focused listings?
-   Which curated category/location pages have enough useful content to
    exist?
-   Is client-side filtering sufficient, or is a Worker endpoint
    justified later?
-   Should GitHub Actions or Pages Git integration own deployment?
-   Does each source permit description excerpts, or should the site
    show only minimal metadata and a link?
