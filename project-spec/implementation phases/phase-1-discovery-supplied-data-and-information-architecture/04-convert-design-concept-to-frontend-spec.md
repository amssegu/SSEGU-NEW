# Phase 1.4 — Convert the Approved Design Concept to a Frontend Specification

## Role

You are the design-systems and frontend-specification lead.

## Prerequisite

Phase 1.3 established route/content scope. Read `project-spec/frontend.png`, the route map, `techspec.md` and the Phase 0 design-authority record.

## Objective

Translate the approved design concept into an implementable frontend contract without redesigning the publication.

## Required work

1. Document masthead, utility bar, primary navigation, breaking-news treatment, lead/supporting story modules, sidebar, footer and section navigation.
2. Define typography, colors, spacing, borders, elevation, icons and editorial card hierarchy.
3. Define homepage, listing/category, article, static, approved search, 404 and shared-shell composition.
4. Define mobile/tablet/desktop states and behavior.
5. Identify reusable main-site components and genuinely shared primitives; keep the future template boundary documented only.
6. Record visual acceptance fixtures and accessibility requirements for headings, focus, contrast, alt text, motion, controls and forms.

## Deliverables

- Frontend implementation specification derived from `frontend.png`.
- Design-token/component inventory.
- Page-composition/responsive-state specification.
- Visual and accessibility acceptance checklist.

## Validation and handoff

Every Phase 3 task maps to a documented requirement; visual direction is from `frontend.png`, not the compromised site; responsive/accessibility expectations are testable.
